# 策划案完整性自检(lr-design 之前的自助工具)

## 定位

`lr-design` 内部有一套完整性判定逻辑(第1步5项核心规则检查 + 第2.5步10项交互细节检查),但这套判定只有在正式发起 `lr-design`、下载文档、建立会话目录之后才会跑一次。策划没有办法在提交前自己反复用同一套标准检验草稿,只能"写完直接扔给 AI,来回改到过关"——这个来回对齐的过程就发生在 lr-design 内部,占用了正式流程的时间。

本技能把这套判定逻辑单独拎出来,做成一个**策划自己能随时反复调用、无副作用、跑完即忘**的自检工具。目标是让策划在飞书上迭代文档的过程中,能随时问一句"如果我现在提交,会被挑出什么问题",自己先把能解决的问题解决掉,再真正发起 `lr-design`。

## 与 lr-design 的关系(重要边界)

- **不修改、不依赖 lr-design 的任何文件**。本技能自带一份独立的检查清单副本(`references/completeness-checklist.md`),不读取 lr-design 目录下的任何内容。
- **判定标准是 lr-design 的超集,不是替代品**。本技能的清单比 lr-design 现有检查项更严格(多了3项范围类检查),这样"precheck 通过"就能大概率意味着"lr-design 第1步也会通过";反过来如果本技能比 lr-design 更宽松,才会出现"precheck 说过了、lr-design 又挑出新问题"的割裂体验,所以宁可查得更严。
- **precheck 通过不代表 lr-design 可以跳过完整性检查**。lr-design 第1步仍然要真实执行判定,原因: (1) 策划可能查完 precheck 后又改了飞书内容; (2) 策划可能压根没用过 precheck 就直接发起 lr-design。precheck 只是把"发现问题、来回修改"的时间提前挪到了策划自己迭代的阶段,不是取消 lr-design 的检查动作本身。
- **不产生任何 lr-design 后续阶段需要读取的产物**。没有决策挂账、没有 change 目录。working.md 只落在本技能自己的 `tmp/` 下,下次调用会先清空,不会被 lr-design 或其他技能读取。策划看完报告后自己回飞书原文修改,不通过本技能的任何文件中转。
- **维护提醒**: `references/completeness-checklist.md` 的前15项是人工从 `lr-design/SKILL.md` 第1步+第2.5步抄录并保持同义(不是逐字复制),如果以后 `lr-design/SKILL.md` 的检查项被修改,需要人工回来核对同步,本技能不会自动感知那边的变化。

## 沟通规则

- 一次性列出本轮发现的全部问题,不逐项来回问——因为没有"策划当场回答、AI 追问"的对话闭环(策划要修改的是飞书原文,不是这次对话),分批提问只会让策划要反复调用本技能才能看到全貌,体验更差。
- 只呈现报告,不代为决策、不建议"应该选哪个方案"——本技能不维护决策挂账,方案取舍留给策划自己在飞书上定稿,定稿后再用 lr-design 的对齐循环走一次正式的决策记录。
- 每次调用都是全新判定,不记住上一次问过什么、策划改了什么。如果策划想知道"我改的地方有没有解决问题",直接重新调用一次即可,不维护跨会话状态。

## 执行流程

命令中 `scripts/`、`references/` 以**本技能目录**为基准。

### 第 1 步:下载策划案到本技能 tmp/ 目录

输入:飞书链接(wiki 或 docx)。运行:

```powershell
python scripts/workflow.py fetch --url <飞书链接>
```

脚本会:
1. 用本技能自己的 `config.json`(飞书应用凭据,与 lr-design 共用同一个飞书应用,但各自维护一份 `config.json` 文件;首次使用需从 `config.json.example` 复制填写)完成认证。
2. **先清空 `tmp/` 下所有历史内容**(与 lr-design 一致的模式,避免跨任务残留污染本次判定),再下载文档正文、转换 Markdown、下载引用图片,全部写入本技能目录下的 `tmp/session/`(不是系统临时目录,不是 `changes/` 下任何位置)。`tmp/` 已加入 `.gitignore`,不会被提交。
3. 过滤"美术需求"类章节(与 lr-design 判定范围保持一致,生产美术不算完整性阻断项)。
4. 输出 working.md 路径,格式为 `WORKING_MD=<路径>`。

若策划直接给的是本地 md 文本或粘贴内容而非飞书链接,跳过下载,直接用该文本作为分析对象,不需要经过脚本(不必写入任何文件,可以直接在对话上下文里分析)。

完成后只说:"已获取策划案《标题》,正在自检..."

### 第 2 步:读取检查清单并逐项判定

1. **读取 working.md 全文**,获取完整策划案内容和结构。
2. **识别文中引用的参考图**,记录图片路径及其所在章节的上下文。
3. **按需读取参考图**,结合引用该图的章节文本理解图片在该上下文中的含义。
4. 读取 [完整性检查清单](references/completeness-checklist.md),逐项(18项)判定,严格按该文件里"判定方法"和"阻断问题 vs 优化建议"的分类标准执行,不要自行发明新标准。

### 第 3 步:输出自检报告

一次性输出完整报告,不分轮次:

```text
玩法理解
用 3~6 条说明对核心循环、目标玩家和主要页面的理解(与 lr-design 首轮审查格式一致,便于策划确认 AI 理解对不对)。

自检结论
若无阻断问题:"可以进入 lr-design 正式流程。"
若有阻断问题:"建议先在飞书补充以下内容,再发起 lr-design,否则大概率会在第一步就被同样问到。"

阻断问题(若有)
逐项列出未通过检查清单第一组(1-5项)或被升级的第三组(16-18项)问题:
- 当前问题
- 影响(不解决会导致什么后果,优先说清楚"lr-design 阶段会怎么被卡住")
- 建议方向(给出思路,不代为拍板)

优化建议(若有)
逐项列出未通过检查清单第二组(6-15项)的问题,说明"这些会在 lr-design 第2.5步被逐项问到,建议提前想清楚"。

提示
本报告为自助自检,不产生任何文件,可在修改飞书文档后随时重新调用本技能复查。
```

不需要主动清理:下一次调用本技能的第1步会先清空 `tmp/`,不会跨任务累积残留。`tmp/` 本身已加入 `.gitignore`,不会被提交(可选:如果同一次对话内需要提前释放,可主动执行 `python scripts/workflow.py cleanup <working.md 所在目录>`,但这不是必须步骤)。

## 完成条件

- 已完整读取策划案文本(及关联图片),按18项清单逐项判定。
- 报告一次性呈现全部问题(阻断+优化建议两组),不分轮次追问。
- 未创建 `changes/` 下任何目录,未创建本技能目录下任何持久文件(除系统临时目录内的下载缓存,不归本技能管理)。
- 策划明确知道下一步:回飞书修改、或直接发起 `/lr-design`。
