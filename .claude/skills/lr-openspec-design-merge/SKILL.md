# OpenSpec Design 合并器

## 角色与目标

面向评审后阶段。输入是评审后的三个详细设计文档（可能包含修改）和评审意见，输出是完整的 design.md，包含精简的架构决策叙事（Context/Goals/Decisions/Risks，供评审和后续查阅）以及三份详细文档的完整附录（供 `lr-openspec-tasks` 读取，不再需要单独读取 design/*.md）。

本 skill 只做合并，不做新的设计工作。

## 核心原则

- design.md 分两部分：**精简叙事**（Context/Goals/Decisions/Risks，回答"为什么这样设计"）+ **完整附录**（三份详细文档原文照搬，回答"具体要建什么"）
- 附录部分是原文并入，不做转述或摘要——摘要转述有失真风险，且下游 `lr-openspec-tasks` 生成任务描述需要协议字段、Record 表列定义、UI 方法签名这类具体细节，摘要会丢失这些信息
- design.md 合并完成后是唯一权威、完整的输入源，`lr-openspec-tasks` 只依赖这一份文件，不再单独读取 design/*.md
- **design/\*.md 是可反复使用的源文件，不是一次性的中间产物**：每次运行本 skill 都会重新读取当前的 design/\*.md 重新合并，不删除、不归档、不假设它们只用一次
- 评审意见如果存在，视为已经直接体现为对 design/\*.md 内容的修改——评审人评审完之后直接编辑三份详细文档本身，本 skill 不维护一份独立的"评审意见"记录
- Open Questions 检查是硬性门槛，且必须在提取叙事、装配附录**之前**执行：如果还有未解决的问题，没有必要浪费工作量去做后续的提取和装配，检查不通过应该是整个流程最先撞到的墙，不是走到最后才发现的意外

## 执行流程

### 第 0 步：输入验证

确认输入：
- `changes/<id>/design.md` 存在（`lr-openspec-design` 生成的初版）
- `changes/<id>/design/client.md` 存在
- `changes/<id>/design/server.md` 存在
- `changes/<id>/design/config.md` 存在

### 第 1 步：读取现有文档

读取四个文档：
- `design.md` - 初版架构决策（`lr-openspec-design` 生成）
- `design/client.md` - 客户端详细设计（可能包含评审后的修改）
- `design/server.md` - 服务端详细设计（可能包含评审后的修改）
- `design/config.md` - 配置表详细设计（可能包含评审后的修改）

### 第 2 步：检查 Open Questions 是否全部回答（硬性门槛，前置执行）

这一步紧跟在读取之后，在做任何提取或装配工作之前执行。不通过就直接中止，不进入第 3、4 步。

**检查逻辑**：
1. 遍历 `design/client.md`、`design/server.md`、`design/config.md` 三份文档各自的 `## Open Questions` 章节
2. 检查每份文档的该章节下是否还有未回答的问题
3. **检查回答质量**（即使有回答，也要判断是否合格）

**判定规则**：

✅ **允许通过**：
- 三份文档的 Open Questions 章节均不存在
- 章节存在但为空（只有标题，没有内容）
- 章节明确标注"全部已解决"

❌ **阻断流程**：
- 任意一份文档的 Open Questions 章节下还有任何未回答的问题
- 即使标注为"低优先级"或"可选"，也不能放行
- **回答质量不合格**（见下文质量检查规则）

**回答质量检查规则**：

即使 Open Questions 有"回答"，也要检查回答质量是否合格：

1. **明确性检查**：
   - 回答中包含"待定""看情况""可能""讨论中""暂不确定""先这样""TBD""TODO"等模糊词汇 → 视为未回答，阻断
   - 回答必须是具体决策，不能是含糊表述

2. **完整性检查**：
   - **协议字段问题**：回答必须包含字段名、类型、取值范围/枚举值（如果适用）
     - 不合格："需要 claimAll 字段"（缺类型）
     - 合格："需要 claimAll 字段，类型 bool，默认 false"

   - **配置表字段问题**：回答必须包含字段定义（名称、类型、示例值）
     - 不合格："需要新增字段"（没说是什么字段）
     - 合格："新增 ShowRemainTime 字段，类型 int，0=不显示 1=显示"

   - **业务逻辑问题**：回答必须包含具体处理策略
     - 不合格："按常规处理"（什么是常规？）
     - 合格："活动结束后，已购买未领取的奖励发邮件补发，有效期 30 天"

3. **可执行性检查**：
   - 拿着这个回答，tasks 环节能否生成具体任务？
   - 如果回答只有结论没有依据 → 警告但不阻断（有决策总比没有强）
   - 如果回答缺少关键信息导致无法生成 tasks → 阻断

**回答质量示例**：

❌ **不合格回答**（需要阻断）：
```markdown
1. **C2S_XXX_Claim 是否需要 claimAll 字段？**
   - 回答：看情况吧，先按现在的做
   - 阻断原因：含有模糊词汇"看情况""先按现在的做"，不是明确决策

2. **FreeHighlight 字段格式？**
   - 回答：需要这个字段
   - 阻断原因：缺少类型定义和格式说明，tasks 无法生成字段定义任务

3. **活动结束后未领取奖励的处理？**
   - 回答：按常规处理
   - 阻断原因："常规处理"模糊，没有说明具体策略
```

✅ **合格回答**：
```markdown
1. **C2S_XXX_Claim 是否需要 claimAll 字段？**
   - 回答：不需要。通过 claimType 参数区分单个(1)/批量(2)领取
   - 理由：复用现有参数，减少协议字段数量
   - 可执行性：tasks 可生成协议定义任务（claimType: int, 1=单个 2=批量）

2. **FreeHighlight 字段格式？**
   - 回答：支持单个 itemID（string 类型）
   - 理由：当前需求只需高亮一个奖励项，多个高亮可后续扩展为分号分隔
   - 可执行性：tasks 可生成配置表字段定义任务

3. **活动结束后未领取奖励的处理？**
   - 回答：已购买未领取的投资奖励发邮件补发，有效期 30 天；免费奖励不补发
   - 理由：投资奖励是付费商品需保障权益，免费奖励是活跃激励过期失效符合设计
   - 可执行性：tasks 可生成邮件发送逻辑任务
```

**阻断时的行为**：

1. 立即停止执行，不进入第 3 步（提取叙事）和第 4 步（装配 design.md），不修改 design.md
2. 输出阻断原因：
   ```text
   ❌ design.md 合并阻断（Open Questions 未全部解决）

   原因：仍有 N 条 Open Questions 未回答 / 回答质量不合格

   未回答或不合格的问题：
   1. [问题描述]
      - 当前回答：[回答内容]
      - 阻断原因：[模糊表述 / 缺少关键信息 / 无法生成 tasks]
      - 来源：design/[client|server|config].md
      - 要求：[需要补充的信息]

   2. [问题描述]
      - 当前回答：[回答内容]
      - 阻断原因：[具体原因]
      - 来源：design/[client|server|config].md
      - 要求：[需要补充的信息]

   下一步：
   1. 回到评审，针对上述问题给出明确、完整、可执行的答案
   2. 更新 design/[client|server|config].md，反映决策结果
   3. 重新运行 lr-openspec-design-merge

   注意：
   - design 环节的 Open Questions 通常涉及协议字段、配置表结构、存储结构等底层技术契约
   - 这些问题的回答必须具体、明确，包含足够信息供 tasks 环节生成任务
   - 模糊的回答（"看情况""待定"）会导致 tasks 环节无法正确拆分任务，增加返工成本
   - 协议/配置表类问题必须包含字段名、类型、取值范围等关键信息
   ```

**设计原则**：
- 为什么检查前置到第 2 步：不通过就没必要做后续的提取和装配工作，检查应该是流程最先撞到的墙，不是走到最后才发现的意外
- 为什么硬性要求全部回答：与 `lr-design` 的"闸门 B：假设清单全部裁决完毕"保持一致，用硬性门槛避免主观判断
- 为什么不区分优先级：如果 Open Questions 生成规则严格执行（排除技术细节、已明确定义、宽泛问题），那剩下的都应该是"不回答就无法继续"的问题
- 为什么阻断而非警告：防止评审流于形式，带着未决问题或模糊答案进入 tasks 会增加返工成本
- **为什么要检查回答质量**：形式上"回答了"但实质模糊（"看情况""待定"），等于没回答，tasks 环节拿到模糊答案仍然无法生成正确任务

### 第 3 步：提取架构叙事

从三个详细文档中提取精简的叙事内容，用于 design.md 的 Decisions 章节（不是给 tasks 用的，是给评审和后续查阅用的）：

**客户端关键决策**：
- 模块设计决策（为什么新增/修改模块）
- Record 表设计决策（为什么需要这些表，为什么这样设计列）
- 协议设计决策（为什么需要这些协议，为什么这样设计参数）
- UI 设计决策（为什么这样组织页面，为什么需要这些状态）
- 红点设计决策（为什么这样设计红点层级）

**服务端关键决策**：
- 模块设计决策（为什么新增/修改模块）
- Record 表设计决策（与客户端对齐的原因）
- 配置表设计决策（为什么需要这些配置表，为什么这样设计字段）
- 业务逻辑设计决策（为什么这样设计流程）
- 性能设计决策（为什么选择这种实现方式）

**配置表关键决策**：
- 新增配置表决策（为什么不能复用现有表）
- 字段设计决策（为什么需要这些字段，为什么选择这种类型）
- 对齐策略决策（如何保证客户端/服务端一致）
- 设计阶段配置表变更（评审确认的变更）

**提取规则**：
- 只提取"为什么"和"备选方案对比"，不提取具体实现（具体实现完整保留在第 4 步的附录中，不会丢失）
- 如果详细文档中有评审后的修改，优先使用修改后的内容

**整合评审中确认的设计变更**（如果评审意见已体现为对 design/\*.md 的修改，这一步自然发生在提取中）：
- 更新 Decisions 章节，反映评审后的最终决策
- 说明变更原因

### 第 4 步：装配完整 design.md

按照以下结构生成/覆盖 `design.md`，注意这不是"提取摘要替换原文"，而是"精简叙事 + 完整原文附录"两部分组成：

```markdown
## Context

[保留初版的背景和当前状态]
[如果评审中发现新的约束，补充到这里]

## Goals / Non-Goals

[保留初版的目标]
[如果评审中调整了范围，更新这里]

**Goals:**
- [设计要达成的目标]

**Non-Goals:**
- [明确排除的范围]

## Decisions

### 客户端设计决策

**模块设计**：[从 client.md 提取的关键决策]
- 决策：[具体决策内容]
- 原因：[为什么这样决策]
- 备选方案：[考虑过的其他方案]
- 为什么不选：[不选备选方案的原因]

**Record 表设计**：[从 client.md 提取]
**协议设计**：[从 client.md 提取]
**UI 设计**：[从 client.md 提取]

详细设计见：本文档附录 A

### 服务端设计决策

**模块设计**：[从 server.md 提取的关键决策]
**Record 表设计**：[从 server.md 提取，对齐说明：与客户端完全对齐]
**配置表设计**：[从 server.md 提取]
**业务逻辑设计**：[从 server.md 提取]

详细设计见：本文档附录 B

### 配置表设计决策

**新增配置表决策**：[从 config.md 提取]
**字段设计决策**：[从 config.md 提取]
**设计阶段配置表变更**：[从 config.md 的"设计阶段配置表变更"章节提取]
**对齐策略**：[从 config.md 提取]

详细设计见：本文档附录 C

## Risks / Trade-offs

[从初版 design.md 和评审后的 design/*.md 中整合]

### 技术风险 / 性能风险 / 兼容性风险
- **风险**：[具体风险描述]
  - 缓解策略：[如何降低风险]

### Trade-offs
- **选择A而非B**：[说明权衡]
  - 优点/缺点/评审结论

## Open Questions

[本节应为空——第 2 步已确认三份文档的 Open Questions 全部解决，走到这一步说明检查已通过]

---

## 附录 A：客户端详细设计

[design/client.md 全文原样并入，不做删减、不做转述]

---

## 附录 B：服务端详细设计

[design/server.md 全文原样并入，不做删减、不做转述]

---

## 附录 C：配置表详细设计

[design/config.md 全文原样并入，不做删减、不做转述]
```

**关键点**：
- Decisions 章节里"详见 design/client.md"这类跨文件链接，改成"详见本文档附录 A"（内容已经在同一份文件里，不需要跨文件跳转）
- 三个附录是原文照搬 design/client.md、design/server.md、design/config.md 的**全部内容**，包括它们各自的 Open Questions 章节——但由于第 2 步已经确认这些章节全部解决，并入后应该显示为"已解决"状态，不会在 design.md 里出现悬而未决的问题
- design.md 的 `## Open Questions` 顶层章节（Decisions 之后、附录之前）此时应为空，因为不存在"评审后剩余的问题"这种情况——第 2 步已经是硬性门槛，走到第 4 步就代表全部解决了

### 第 5 步：运行 openspec validate

运行 `openspec validate <id>`，确保：
- design.md 格式符合 OpenSpec 标准
- proposal.md、specs/*.md 仍然合法

如果 validate 失败，修复错误后重新运行。

### 第 6 步：输出交接摘要

输出交接摘要：

```text
变更名: <id>
design.md 合并完成:
  - 已整合客户端、服务端、配置表的关键设计决策（Decisions 章节）
  - 已完整并入三份详细设计文档（附录 A/B/C）
  - Open Questions: ✅ 全部已解决（第 2 步硬性检查已通过）

openspec validate: ✅ 通过

下一步: 进入 tasks 环节
  - design.md 是唯一需要读取的输入（叙事 + 完整附录），lr-openspec-tasks 不再单独读取 design/*.md
  - tmp/*-implementation-details.md 作为实现参考（如果存在）
```

**注意**：只有第 2 步检查通过才会走到这里输出上述摘要。如果第 2 步检查不通过，流程在那一步就已经中止并输出阻断信息，不会执行第 3、4、5、6 步。

## 完成条件

- `changes/<id>/design.md` 已更新，包含精简叙事（Decisions）+ 完整附录（design/*.md 原文）
- **第 2 步 Open Questions 检查已通过**（三份详细文档的 Open Questions 全部回答且质量合格）—— 硬性要求，且检查发生在提取和装配之前
- `openspec validate <id>` 通过
- 输出交接摘要，明确"design 合并完成，可以进入 tasks"

**如果第 2 步检查未通过**：
- 流程在该步骤直接中止，不执行提取和装配
- 不满足完成条件，不修改 design.md
- 输出阻断信息，要求回到评审解决问题

## 不做的事

- 不做新的设计决策（只整合已有的）
- 不修改三份详细文档 design/*.md（只读取，它们是可反复使用的源文件）
- 不删除或归档 design/*.md（每次运行都会重新读取当前版本，它们不是一次性中间产物）
- 不生成 tasks.md（那是下一个环节）
- 不单独维护评审意见记录（假设评审意见已体现为对 design/*.md 的直接修改）

## 使用场景

```
评审流程：
1. lr-openspec-design 生成 design.md（初版）+ design/*.md（详细）
2. 前端/后端/策划分别评审 design/*.md，提出修改意见
3. 修改 design/*.md，反映评审结果（评审意见直接体现为文档修改）
4. 使用 lr-openspec-design-merge：
   - 先检查三份文档的 Open Questions 是否全部解决（硬性门槛）
   - 通过后装配 design.md（精简叙事 + 完整附录）
5. design.md 作为最终技术设计文档，进入 tasks 环节
   （lr-openspec-tasks 每次运行都会先重新触发本 skill，
    确保读到的 design.md 反映的是当前最新的 design/*.md）
```

## 路径约定

- **openspec 根**：包含 config.yaml 的目录
- **changes 目录**：`<openspec根>/changes/<id>/`
- **合并后设计**（叙事 + 完整附录）：`<changes目录>/design.md`
- **详细设计源文件**（持续可编辑，不归档）：`<changes目录>/design/*.md`
- **实现细节**：`<openspec根>/tmp/*-implementation-details.md`
