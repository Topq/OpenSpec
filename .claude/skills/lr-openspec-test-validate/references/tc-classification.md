# TC 分类规则

## 五类

| 类型 | 名称 | 特征 | 处理 |
|---|---|---|---|
| **1** | 静态可验证 | 纯逻辑分支、状态机、防重复、边界保护 | 读源码判定，产出 `static_passed/failed` |
| **2a-struct** | 运行时结构可验证 | 面板打开、元素存在、文案数值、状态显隐 | 走 Unity 运行时 4a（C1/C2） |
| **2a-interact** | 运行时交互可验证 | 滚动、切页、展开、按钮响应、关闭 | 走 Unity 运行时 4b（C3），**必须真操作** |
| **2b** | 人工测试 | 像素级视觉、真实支付、多设备、需要人眼判断 | 进人工清单 |
| **3** | 联调测试 | Record 写入、服务端校验、跨端同步 | 进联调清单 |

## 判定顺序

```
先看是否必须服务端/真实数据才能得出结论
  → 是：类型 3（除非客户端侧有独立可验证部分，拆开）
再看是否需要“操作 UI 并观察反馈”才能得出结论
  → 是：类型 2a-interact
再看是否必须真实运行 UI 才能看到结构与状态
  → 是：类型 2a-struct
再看是否涉及真实支付/多设备/像素级视觉
  → 是：类型 2b
否则：类型 1
```

**2a-struct 与 2a-interact 必须分开。** 以前统一叫 2a，导致“面板打开了、字段绑对了”就被当成验证完成，实际一次交互都没做。分开后：

- 2a-struct 只证明“看起来对”
- 2a-interact 才证明“用起来对”
- 只完成 2a-struct 的面板，判定上限是 `runtime_config_only`

## 关键词参考（仅辅助，不替代语义判断）

| 关键词 | 倾向 |
|---|---|
| 点击、滑动、拖动、切页、展开收起、关闭 | 2a-interact |
| 打开、显示、隐藏、置灰、文案、数值、图标 | 2a-struct |
| 服务端、Record 表、协议返回、发货、跨端、重登 | 3 |
| SDK 支付、真机、多设备、像素、美术还原 | 2b |
| 防重复、边界、条件判断、状态机、空值保护 | 1 |

**不要只靠关键词**：同一句“点击领取后按钮置灰”里，“点击”是 2a-interact 的操作，“置灰”是 1 的状态判定。要允许**一条 TC 拆成多个验证点**，分别归类和给结论。

## 运行前置与降级

2a 不是“一定跑得成”。分类时同时记录它的**运行前置**：

- 需要哪个面板、入口级别（real / gm / L2 / L3）
- 需要什么账号/等级/活动状态
- 需要哪些数据（真实 / GM / mock）

前置门禁不过时，**降级并写清原因**：

| 情况 | 降级为 |
|---|---|
| 面板打不开 / 数据造不出 | `2b`，`downgraded_to_manual(reason)` |
| 面板能打开但交互链不可用（无 EventSystem） | 2a-interact → `runtime_blocked_tooling`，保留 2a-struct 结论 |
| 交互是 unsafe（支付/领取） | `2b`，`unsafe(reason)` |

禁止把“没跑成”标成“通过”。

## 输出格式

```
TC-id | 标题
  类型: 1 / 2a-struct / 2a-interact / 2b / 3
  验证点:（可多条，分别归类）
  运行前置:（仅 2a；含入口级别）
  处理: 静态 / 4a / 4b / 人工 / 联调
```

## 格式异常

`test-cases.md` 解析不了时：

- 能提取 TC ID 和标题 → 保留，验证点标“格式异常，待人工确认”
- 完全提取不了 → 整条归入人工清单，并单列“格式问题”

不要为了凑分类去猜内容。
