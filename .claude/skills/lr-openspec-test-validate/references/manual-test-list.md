# 人工测试清单

## 来源

收四类：

- **2b**：静态和运行时的能力边界之外（真实支付、多设备、像素级视觉）
- **3**：需要服务端/真实数据/跨端
- **unsafe 交互**：规则禁止自动执行（购买、领取、消耗、写存档）
- **entry_unverified**：只靠 L2/L3 注入打开的面板，真实入口未验证

**2a-struct / 2a-interact 里已经验证过的条目必须从清单中扣除**，并在清单开头写明扣除了多少项、为什么。

---

## 每条必须包含

```
- [ ] TC-id 标题
  - 前置条件：
  - 操作步骤：
  - 预期结果：
  - 验证点：
  - 类型：2b / 3 / unsafe / entry_unverified
  - 环境要求：（服务端 / 账号 / 真机 / 支付沙箱 …）
```

缺任何一项都视为不合格，回补充。

---

## unsafe 交互怎么写

这类条目**不能**照抄“点一下按钮看看”。必须写清为什么不能自动做，以及人工执行后要看什么。

```
- [ ] TC-x 购买按钮
  - 前置条件：账号有 X 活动资格，钱包余额充足，活动已开启
  - 操作步骤：进入活动页 → 点击卡片购买按钮 → 在支付弹窗确认
  - 预期结果：弹出购买面板，价格/道具与配置一致；确认后扣款并发货
  - 验证点：支付面板打开 / 道具展示 / 扣款 / 发货 / 红点变化
  - 类型：unsafe（handler: RechargeHelper.DoPay）
  - 为什么不能自动：会触发真实支付
  - 环境要求：支付沙箱 + 测试账号
```

要求：

- 写出 unsafe 的**具体原因**（handler 名或危险调用）
- 与 TC ID 对齐，避免和原有 TC 重复计费
- 同一个 unsafe 元素只列一条，不按点击次数拆

---

## entry_unverified 怎么写

本次只通过 L2（合成菜单数据）或 L3（`ui-open`）打开过面板时：

- 单列一组，写明 `entry=synthetic_setactivity` / `injected_ui_open`
- 步骤从**主界面入口**开始，覆盖入口可见性、点击后的加载、活动未开启/已结束的显示
- **不能**因为面板内部验过就从清单扣除

---

## 分组

- 按功能模块分组（购买、领取、显示、联调）
- 同类型放在一起，减少环境切换
- 联调类单独成组，标注需要哪些环境
- unsafe 与 entry_unverified 各自成组
- 每组开头写明条目数

---

## 优先級建议

1. 核心流程（购买、领取、入口）
2. 高严重度边界（背包满、重复领取、失败回滚）
3. 联调（前后端真实交互）
4. 视觉/体验类

---

## 与缺陷清单的关系

- 人工清单里的条目是“还没验的”
- 缺陷清单里的是“已经验出有问题的”
- 不要把同一条同时放进两边

---

## 格式技巧

长清单不要逐条展开全部细节，可按组折叠；但**保留 TC ID**，保证可追溯。

`test-cases.md` 格式异常、无法解析的条目，单独放“格式问题”小节，不硬塞进正常分组。
