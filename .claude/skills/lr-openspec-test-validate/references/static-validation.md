# 静态验证（类型 1）

## 目标

对不依赖运行时的 TC，用源码给出可追溯结论：**在哪里、看到什么、所以判定什么**。这是 AI 辅助的代码审查，不是自动化证明。

## 取证优先级

1. **CodeGraph**：工程根有 `.codegraph/` 时优先用 `codegraph_explore`，一次拿到符号源码和调用路径
2. **Grep + Read**：没有 CodeGraph 时，先 grep 定位 ≥2 处参考实现或调用点，再读完整函数
3. **禁止只看命名下结论**：方法叫 `CheckBagFull` 不等于调用链真的生效

## 客户端验证路径

```
入口（按钮/协议/事件）
  → 处理函数
  → 关键分支（if/else、状态判定、防重复）
  → 下游调用（Module / Record / 协议发送）
```

每步记录文件:行号和代码片段。

## 服务端验证路径

```
协议命令注册
  → 处理函数
  → 权威校验（条件、等级、重复领取）
  → Record 写入 / 物品发放
  → 失败回滚
```

## 证据格式

```
TC-id：结论
- 验证方法：追踪 XXX → YYY
- 代码位置：path:line（可多行）
- 关键片段：`if (HasClaimed) return;`
- 判定：通过 / 未覆盖 / 无法判定
- 说明：为什么这段代码足以/不足以支撑该验证点
```

## 常见误判

| 误判 | 纠正 |
|---|---|
| 字段/方法存在 = 逻辑生效 | 必须看到调用链真的走到 |
| 只在客户端找到分支 = 服务端也校验 | 服务端未实现时，服务端半边标“未验证” |
| 注释说“已处理” = 代码已处理 | 以代码为准 |
| 一个函数覆盖多个 TC | 每个 TC 单独给结论，不合并 |
| 静态通过 = 功能通过 | 静态只证明代码路径存在，不证明运行时表现 |

## 边界

**能做**：
- 分支是否存在
- 调用是否发生
- 状态字段是否被读写
- 协议是否在预期位置发送

**不能做**：
- UI 实际显示
- 网络真实返回
- 时序/并发/性能
- 服务端未实施的部分

## 输出

每条类型 1 TC 一条记录；无法判定的写 `inconclusive` 并说明缺什么，不要凑成“通过”。
