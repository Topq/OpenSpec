# design-config.md 生成规则（精简版 v2）

> **说明**: 本文档定义 design-config.md 的生成规则。
> 该文档从 proposal.md 和 specs/*.md 生成，用于策划和技术联合评审配置表设计。
> 
> **设计哲学**: 规则文件只包含"无法从代码推理的知识"，所有代码模板通过 CodeGraph 查询获取。
> **策划权限约束**: 策划只有配置表权限，无前后端程序代码权限。所有涉及代码的决策必须联合前后端工程师。

## 零、Pre-flight Check（代码库调查）

在生成 design-config.md 之前，**必须先执行代码库调查**，避免基于错误假设设计。

### 调查清单

| 调查项 | 查询方式 | 目的 |
|-------|---------|------|
| **配置表是否已存在** | Glob: `D:/se/design/table/default_ios/*.xlsx` | 判断是新增还是扩展 |
| **字段是否由代码固定** | CodeGraph: `struct CGrowthFundConfig TDGrowthFund` (客户端)<br>CodeGraph: `struct STGrowthFund` (服务端) | 识别固定字段 |
| **导出机制是否特殊** | 检查自定义导出脚本 | 确认非标准流程 |

### 调查结果的文档体现

调查结果必须体现在 design-config.md 的以下位置：

1. **`## ⚠️ 当前状态` 章节**（若字段由代码固定或与 proposal 假设冲突）
2. **`## 背景与目标`**（简要说明是新增表还是扩展表）
3. **`## ⚠️ 设计阶段配置表变更` 章节**（区分三种场景）

## 一、配置表变更的三种场景判断流程

<!-- 来源：从真实代码归纳（EquipSuitRecastDefine.h, AIDefine.h, AccFirstRechargeDefine.h） -->

### 判断流程图

```
配置表是否已存在？
  ├─ 否 → 场景 1：新增配置表
  └─ 是 → 字段是否由代码固定？
       ├─ 是 → 场景 3：字段由代码固定
       └─ 否 → 场景 2：扩展现有配置表
```

---

### 具体判断方法

#### 步骤 1：配置表是否已存在

**查询方式**：
```bash
# 在策划配置目录搜索
find D:/se/design/table/default_ios -name "*growth_fund*.xlsx"
```

**判断标准**：
- 若找到 → 进入步骤 2
- 若未找到 → **场景 1：新增配置表**

---

#### 步骤 2：字段是否由代码固定

**查询方式**：
```
CodeGraph 查询（客户端）：
  struct CGrowthFundConfig TDGrowthFund 配置结构体

CodeGraph 查询（服务端）：
  enum ConditionType DisplayType <字段名>Type
```

**判断标准**：
- 若查询结果包含 `enum <字段名>Type { ... }` → **场景 3：字段由代码固定**
- 若查询结果未包含枚举定义 → **场景 2：扩展现有配置表**

**示例**（场景 3）：
```cpp
// 服务端 ConditionModule.h 中发现枚举定义
enum
{
    COND_TYPE_LEVEL = 1,      // 等级
    COND_TYPE_TOWER = 2,      // 爬塔
    COND_TYPE_LOGIN = 3,      // 累计登录
    COND_TYPE_MAX,
};
```
→ `ConditionType` 字段由代码固定，策划只能填 1、2、3

**示例**（场景 2）：
```cpp
// 配置结构体中未发现枚举定义
struct STGrowthFundMainConfig
{
    int nActiveId;
    fast_string strName;  // 自由填写的字符串，无枚举限制
    int nSortOrder;       // 自由填写的整数，无枚举限制
};
```
→ `Name` 和 `SortOrder` 字段可自由扩展

### 场景 3：字段由代码固定（不可自由调整）

**标注方式**（在字段定义表的"状态"列）：
```markdown
| 字段名 | 类型 | 说明 | 示例值 | 必填 | 状态 |
|--------|------|------|--------|------|------|
| DisplayType | int | 显示类型：1=自然时间, 2=永久 | 1 | 是 | 🔒 代码固定（枚举），策划只能填 1 或 2 |
| ConditionType | int | 条件类型：1=等级, 2=爬塔, 3=累计登录 | 1 | 是 | 🔒 代码固定（枚举），不可自由扩展 |
```

**说明文本**（在配置表章节顶部）：
```markdown
**⚠️ 固定字段约束**：
以下字段由代码固定，策划只能填写预定义的枚举值，不可自由调整：
- `DisplayType`：只能填 1（自然时间）或 2（永久）
- `ConditionType`：只能填 1（等级）、2（爬塔）、3（累计登录）

若需新增枚举值（如 DisplayType=3），需要前后端工程师修改代码后才能使用。
```

## 二、配置表生成和使用机制

以下流程是**跨角色的独特知识**，AI 无法从代码推理。

### 2.1 策划侧流程

```
策划在 `D:/se/design/table/default_ios` 编辑 Excel 配置表
  ↓
Excel 保存后自动导出为 txt 文件
  ↓
txt 文件提交到版本控制
```

---

### 2.2 服务器侧流程

```
服务器直接读取 txt 文件
  ↓
使用自定义解析代码解析为 C++ 结构体
  ↓
加载到内存 (std::map)
```

**关键约定**：
- 使用 `READ_FILE` 宏读取 txt 文件
- 使用 `txt.ReadInt(i, "FieldName")` 按字段名读取（字段名必须与 Excel 列名完全一致，大小写敏感）
- 使用 `LogicAssert` 检查主键不重复
- 使用 `std::map` 存储配置，主键作为 key

**代码模板获取**：
```
CodeGraph 查询：LoadResource READ_FILE txt.ReadInt 配置加载
参考模块：AccrueRechargeModule, CardModule
```

---

### 2.3 客户端侧流程

```
配置表 txt 更新后
  ↓
运行 `D:\se\develop\client\tools\table\output_code_csharp.bat`
  ↓
自动生成 C# 解析结构类 (TDXXXTable.cs)
  ↓
⚠️ 在 `TableConfig.cs` 中注册新表（重要！经常遗漏）
  ↓
客户端通过生成的类访问配置数据
```

**关键约定**：
- 注册位置：`Assets/Script/Table/TableConfig.cs`
- 注册方式：在 `delayLoadTableArray` 数组中添加 `TDXXXTable.metaData`

---

### 2.4 对齐要求

**必须对齐的项**（阻断性）：

| 对齐项 | 客户端 | 服务器 | 要求 |
|-------|--------|--------|------|
| **字段顺序** | 按 Excel 列顺序 | 按 txt 列顺序 | 必须完全一致 |
| **数据类型** | C# 类型 | C++ 类型 | int↔int, string↔fast_string, float↔float |
| **空值处理** | 默认值或null | 空字符串或0 | 必填字段不允许为空 |

**回答质量检查**（设计合并门禁）：

### 3.1 禁止模糊词汇（阻断性）

## 六、常见问题 FAQ

### Q1: 如何判断应该新增配置表还是扩展现有表？

**A**: 执行 Pre-flight Check：
1. 在策划配置目录搜索类似表名
2. 若找到 → 检查字段是否匹配 → 扩展现有表
3. 若未找到或字段差异大 → 新增配置表

---

### Q2: 如何识别字段是否由代码固定？

**A**: 通过 CodeGraph 查询客户端/服务端的配置结构体定义，若发现枚举值硬编码，则为固定字段。

---

### Q3: 配置表字段定义应该包含哪些列？

**A**: 必需列：字段名、类型、说明、示例值、必填、客户端使用、服务器使用、状态

**状态列**的可能值：
- `proposal已提`：proposal 中已明确提及
- `⚠️ 设计阶段补充`：设计阶段发现必须补充
- `🔒 代码固定`：由代码固定，不可自由调整
