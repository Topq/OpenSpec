# design-config.md 生成规则（精简版 v2）

> **说明**: 本文档定义 design-config.md 的生成规则。
> 该文档从 proposal.md 和 specs/*.md 生成，用于策划和技术联合评审配置表设计。
> 
> **设计哲学**: 规则文件只包含"无法从代码推理的知识"，所有代码模板通过 CodeGraph 查询获取。
> **策划权限约束**: 策划只有配置表权限，无前后端程序代码权限。所有涉及代码的决策必须联合前后端工程师。

## 零、Pre-flight Check（代码库调查）

在生成 design-config.md 之前，**必须先执行代码库调查**，避免基于错误假设设计。

### 调查清单

| 调查项 | 查询方式 | 目的 |
|-------|---------|------|
| **配置表是否已存在** | Glob: `../design/table/default_ios/*.xlsx` | 判断是新增还是扩展 |
| **字段是否由代码固定** | CodeGraph: `struct CGrowthFundConfig TDGrowthFund` (客户端)<br>CodeGraph: `struct STGrowthFund` (服务端) | 识别固定字段 |
| **导出机制是否特殊** | 检查自定义导出脚本 | 确认非标准流程 |

### 调查结果的文档体现

调查结果必须体现在 design-config.md 的以下位置：

1. **`## ⚠️ 当前状态` 章节**（若字段由代码固定或与 proposal 假设冲突）
2. **`## 背景与目标`**（简要说明是新增表还是扩展表）
3. **`## ⚠️ 设计阶段配置表变更` 章节**（区分三种场景）

## 一、配置表变更的三种场景判断流程

<!-- 来源：从真实代码归纳（EquipSuitRecastDefine.h, AIDefine.h, AccFirstRechargeDefine.h） -->

### 判断流程图

```
配置表是否已存在？
  ├─ 否 → 场景 1：新增配置表
  └─ 是 → 字段是否由代码固定？
       ├─ 是 → 场景 3：字段由代码固定
       └─ 否 → 场景 2：扩展现有配置表
```

---

### 具体判断方法

#### 步骤 1：配置表是否已存在

**查询方式**：
```bash
# 在策划配置目录搜索
find ../design/table/default_ios -name "*growth_fund*.xlsx"
```

**判断标准**：
- 若找到 → 进入步骤 2
- 若未找到 → **场景 1：新增配置表**

---

#### 步骤 2：字段是否由代码固定

**查询方式**：
```
CodeGraph 查询（客户端）：
  struct CGrowthFundConfig TDGrowthFund 配置结构体

CodeGraph 查询（服务端）：
  enum ConditionType DisplayType <字段名>Type
```

**判断标准**：
- 若查询结果包含 `enum <字段名>Type { ... }` → **场景 3：字段由代码固定**
- 若查询结果未包含枚举定义 → **场景 2：扩展现有配置表**

**示例**（场景 3）：
```cpp
// 服务端 ConditionModule.h 中发现枚举定义
enum
{
    COND_TYPE_LEVEL = 1,      // 等级
    COND_TYPE_TOWER = 2,      // 爬塔
    COND_TYPE_LOGIN = 3,      // 累计登录
    COND_TYPE_MAX,
};
```
→ `ConditionType` 字段由代码固定，策划只能填 1、2、3

**示例**（场景 2）：
```cpp
// 配置结构体中未发现枚举定义
struct STGrowthFundMainConfig
{
    int nActiveId;
    fast_string strName;  // 自由填写的字符串，无枚举限制
    int nSortOrder;       // 自由填写的整数，无枚举限制
};
```
→ `Name` 和 `SortOrder` 字段可自由扩展

### 场景 3：字段由代码固定（不可自由调整）

**标注方式**（在字段定义表的"状态"列）：
```markdown
| 字段名 | 类型 | 说明 | 示例值 | 必填 | 状态 |
|--------|------|------|--------|------|------|
| DisplayType | int | 显示类型：1=自然时间, 2=永久 | 1 | 是 | 🔒 代码固定（枚举），策划只能填 1 或 2 |
| ConditionType | int | 条件类型：1=等级, 2=爬塔, 3=累计登录 | 1 | 是 | 🔒 代码固定（枚举），不可自由扩展 |
```

**说明文本**（在配置表章节顶部）：
```markdown
**⚠️ 固定字段约束**：
以下字段由代码固定，策划只能填写预定义的枚举值，不可自由调整：
- `DisplayType`：只能填 1（自然时间）或 2（永久）
- `ConditionType`：只能填 1（等级）、2（爬塔）、3（累计登录）

若需新增枚举值（如 DisplayType=3），需要前后端工程师修改代码后才能使用。
```

## 二、配置表生成和使用机制

以下流程是**跨角色的独特知识**，AI 无法从代码推理。

### 2.1 策划侧流程

```
策划在 `../design/table/default_ios` 编辑 Excel 配置表
  ↓
Excel 保存后自动导出为 txt 文件
  ↓
txt 文件提交到版本控制
```

---

### 2.2 服务器侧流程

```
服务器直接读取 txt 文件
  ↓
使用自定义解析代码解析为 C++ 结构体
  ↓
加载到内存 (std::map)
```

**关键约定**：
- 使用 `READ_FILE` 宏读取 txt 文件
- 使用 `txt.ReadInt(i, "FieldName")` 按字段名读取（字段名必须与 Excel 列名完全一致，大小写敏感）
- 使用 `LogicAssert` 检查主键不重复
- 使用 `std::map` 存储配置，主键作为 key

**代码模板获取**：
```
CodeGraph 查询：LoadResource READ_FILE txt.ReadInt 配置加载
参考模块：AccrueRechargeModule, CardModule
```

---

### 2.3 客户端侧流程

```
配置表 txt 更新后
  ↓
运行 `..\develop\client\tools\table\output_code_csharp.bat`
  ↓
自动生成 C# 解析结构类 (TDXXXTable.cs)
  ↓
⚠️ 在 `TableConfig.cs` 中注册新表（重要！经常遗漏）
  ↓
客户端通过生成的类访问配置数据
```

**关键约定**：
- 注册位置：`Assets/Script/Table/TableConfig.cs`
- 注册方式：在 `delayLoadTableArray` 数组中添加 `TDXXXTable.metaData`

---

### 2.4 对齐要求

**必须对齐的项**（阻断性）：

| 对齐项 | 客户端 | 服务器 | 要求 |
|-------|--------|--------|------|
| **字段顺序** | 按 Excel 列顺序 | 按 txt 列顺序 | 必须完全一致 |
| **数据类型** | C# 类型 | C++ 类型 | int↔int, string↔fast_string, float↔float |
| **空值处理** | 默认值或null | 空字符串或0 | 必填字段不允许为空 |

## 四、文档结构模板

### 4.1 必需章节

```markdown
# Design: {功能名称} - Config

## ⚠️ 当前状态（若 Pre-flight Check 发现字段由代码固定）

## 背景与目标

## ⚠️ 设计阶段配置表变更
（新增表、补充字段、关联变更）

## 配置表生成和使用机制
（策划/服务器/客户端三端流程）

## 配置表定义
（完整字段定义，包含"状态"列标注）

### {配置表1}
**表文件路径**: `../design/table/default_ios/{table_name}.xlsx`
**状态**: ⚠️ 新增配置表 / 扩展现有表 / 部分字段由代码固定

**完整字段定义**:
| 字段名 | 类型 | 属性 | 说明 | 示例值 | 必填 | 客户端使用 | 服务器使用 | 状态 |

**属性列说明（强制）**：
- **S（Server）**：仅服务端使用的字段，客户端不加载/不解析（如服务端内部计算用的中间值、权限校验字段）
- **C（Client）**：仅客户端使用的字段，服务端不加载/不解析（如客户端UI展示用的本地化key、特效ID、排序权重）
- **A（All）**：双端都使用的字段，必须在服务端和客户端的配置结构体中都定义（如活动ID、奖励内容、条件阈值）

**属性标注规则**：
1. **每个字段必须明确标注 S/C/A**，不允许留空或"待定"
2. **判断依据**：
   - 字段是否出现在服务端 `READ_FILE` 加载的结构体中 → 包含S或A
   - 字段是否出现在客户端生成的 `TDXXXTable.cs` 类中 → 包含C或A
   - 字段仅用于服务端业务逻辑（如权限校验、发奖条件判断） → S
   - 字段仅用于客户端UI展示（如特效ID、UI排序、本地化key） → C
   - 字段用于双端协议通信或共同的业务逻辑 → A
3. **灰色地带处理**：
   - 如果字段未来可能被另一端使用，优先标记为 A（扩展性优先）
   - 如果字段明确只在一端使用且另一端永远不需要，标记为 S 或 C（节省解析开销）
4. **验证方式**：
   - 用 CodeGraph 查询服务端结构体定义（如 `struct STGrowthFundMainConfig`）
   - 用 Grep 查询客户端生成的配置类（如 `TDActiveFundMain.cs`）
   - 对比两端字段列表，确认属性标注的准确性

**关联配置表**:
（若有关联）

### 客户端代码生成配置（强制）

> SE 专有生成规则：先读 `schemas/lr-func-dev/rules/common/se-config-generation.md`；`need_copy` 与 `NeedParseDataMethod` 分开判断，S 字段动态解析走工具临时转换，源表必须恢复。

**outcode_config.json 配置建议**

配置文件位置：`..\develop\client\tools\table\table_config\outcode_config.json`

#### 1. need_copy 配置
**作用**：标记哪些配置表需要生成客户端 C# 代码

**配置规则**：
- ✅ **需要配置**：配置表包含 **C 字段**（Client-only）或 **A 字段**（All）
- ❌ **不需要配置**：配置表全部为 **S 字段**（Server-only）且客户端完全不读取

**判断流程**：
1. 查看上方"完整字段定义"表格的"属性"列
2. 如果存在任何 C 或 A 字段 → 需要添加到 `need_copy` 数组
3. 如果全部为 S 字段 → 不需要配置

**本配置表结论**：
- [ ] 需要添加到 `need_copy`（包含 C 或 A 字段）
- [ ] 不需要添加（纯 S 字段）

#### 2. NeedParseDataMethod 配置
**作用**：标记哪些配置表需要生成 `ParseData` 方法（支持动态配置下发）

**配置规则**：
- ✅ **需要配置**：客户端使用生成表类进行运行时动态解析，例如整表动态配置同步；活动、非活动及 S/C/A 各种归属均按实际解析链判断
- ❌ **不需要配置**：满足以下任一条件
  - 静态配置表（打包时加载，运行时不变）
  - 仅通过独立业务协议传值、未使用生成表类动态解析的配置
  - 纯静态 C 字段表（客户端专属，无动态解析需求）

**判断流程**：
1. 确认配置加载方式（见下方"配置加载方式"说明）
2. 如果需要生成客户端表类的动态解析能力 → 添加到 `NeedParseDataMethod` 数组；纯业务协议直接下发且不用本地表解析的情况不加入
3. 如果只做静态加载或独立业务协议传值、不使用生成表类动态解析 → 不需要配置；不能以非活动直接豁免

**配置加载方式**（必须明确标注）：
- [ ] **静态配置**：打包时从 txt 文件加载，运行时不可调整（如怪物属性、技能配置）
- [ ] **动态配置**：服务端可在运营期间调整，通过协议推送到客户端（如活动奖励档位、任务目标）

**⚠️ 动态配置的实际同步入口核查（阻断性）**：

判定为“动态配置”时，先读 `rules/common/se-config-generation.md`（相对于 schema 根目录），对每张表记录实际入口及 SE 源码依据。一个功能涉及多条链时分表、分入口说明；不凭“活动”或“动态”标签选择加载宏。

| 实际入口 | 服务端核查 | 客户端核查 | 不得误套的要求 |
|---|---|---|---|
| 旧活动文件拉取链 | 目标文件经 `READ_SYNC_FILE` 或已核实的等价注册进入 ConfigSyncModule 的文件同步集合 | `DynamicConfigModule` 表级适配；`IConfigSyncMethod` 活动级注册；按加载时机填写 `fileNameList` / `preFileNameList`，任一可为空 | 不把只有 `READ_FILE` 且无其他同步注册的文件当作已接入此链 |
| 数据库配置同步 | 实际数据库配置登记、版本及同步发送入口 | 首次主角 Ready 请求、版本计划、`OnDataBaseConfigSync` 回包和对应表的动态解析 | 不强制 `READ_SYNC_FILE`、`IConfigSyncMethod` 或补造活动类型 |
| 独立业务协议传值 | 权威数据来源、协议字段与发送时机 | 接收、更新及消费路径；若仍使用生成表类动态解析，另查表级适配 | 不因协议携带配置数据就自动要求活动文件同步宏 |

入口无法确认时，在设计中列出待核实项并补齐证据；不得自动选择旧活动链，也不得直接宣称“不需要服务端改动”。

**旧活动文件拉取链的专项检查**（仅命中该入口时执行）：

1. 按 CodeGraph 优先规则查询 SE 同类模块与目标文件的 `READ_SYNC_FILE` / `READ_FILE`、`load_sync_file`、`ConfigSyncModule::LoadFile`；没有索引或工具不可用时再用定点文本查询。
2. `ConfigSyncModule` 只同步显式注册的文件：`READ_SYNC_FILE` 调用 `load_sync_file()` → `ConfigSyncModule::LoadFile()`，客户端用 `CLIENT_CUSTOMMSG_PULL_CFGSYNC_FILES` 拉取文件同步集合中的表。核对目标文件实际注册，不能仅因参考模块用了该宏就判当前文件已接入。
3. 目标文件只有 `READ_FILE`、无其他同步注册且确需走本链时，在 design/server.md 说明所需接入，在后续服务端任务中列出对应宏/注册修改；新建文件也按本链设计接入。已注册则注明复用证据，不重复改造。

**数据库配置同步 / 独立协议的专项检查**：

- 按对应入口核对实际 SE 服务端登记/发送与客户端请求/回包处理；数据库路径包含版本计划与表级解析注册，独立协议包含字段及消费方。
- 缺失哪一段，就在三端设计中说明并在后续任务阶段拆对应任务；不将缺失项一律转换成“改用 READ_SYNC_FILE”。
- `NeedParseDataMethod` 仍按是否需要生成客户端表类的动态解析能力独立判断，不由入口名称或 S/C/A 归属自动决定。

**禁止的错误假设**：
- ❌ “ConfigSyncModule 自动扫描任意 txt 文件”或“活动配置天然已接入同步”。
- ❌ “只要客户端接入 DynamicConfigModule 就能收到数据”。
- ❌ “所有动态配置都必须使用 READ_SYNC_FILE”，或“看到 READ_FILE 就能断定数据库/独立协议也无法同步”。

**本配置表结论**：
- [ ] 需要添加到 `NeedParseDataMethod`（需要客户端表类动态解析）
- [ ] 不需要添加（仅静态加载或独立业务协议，不用生成表类动态解析）
- 实际同步入口：旧活动文件拉取 / 数据库配置同步 / 独立业务协议（多入口分别说明）
- 服务端登记/发送与客户端请求/解析的源码依据：[填写路径、入口及结论]
- 已接入部分与缺失接入任务：[按实际入口填写；不适用写明理由]

**配置示例**：
```json
// 需要同时添加到两个数组的情况（动态活动配置表）
{
  "need_copy": [
    "activity_koi",
    "activity_koi_reward"
  ],
  "NeedParseDataMethod": [
    "activity_koi",
    "activity_koi_reward"
  ]
}

// 只添加到 need_copy 的情况（静态配置，包含 C/A 字段）

    "monster_attribute",
    "skill_config"
  ],

## 六、常见问题 FAQ

### Q1: 如何判断应该新增配置表还是扩展现有表？

**A**: 执行 Pre-flight Check：
1. 在策划配置目录搜索类似表名
2. 若找到 → 检查字段是否匹配 → 扩展现有表
3. 若未找到或字段差异大 → 新增配置表

---

### Q2: 如何识别字段是否由代码固定？

**A**: 通过 CodeGraph 查询客户端/服务端的配置结构体定义，若发现枚举值硬编码，则为固定字段。

---

### Q3: 配置表字段定义应该包含哪些列？

**A**: 必需列：字段名、类型、说明、示例值、必填、客户端使用、服务器使用、状态

**状态列**的可能值：
- `proposal已提`：proposal 中已明确提及
- `⚠️ 设计阶段补充`：设计阶段发现必须补充
- `🔒 代码固定`：由代码固定，不可自由调整
