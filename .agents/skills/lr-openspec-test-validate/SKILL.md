# lr-openspec-test-validate

> **职责**: 分析 test-cases.md 的测试用例覆盖情况，静态验证能验证的，输出人工测试清单给无法静态验证的。
> **阶段**: 阶段 11b
> **依赖**: apply 阶段完成（不依赖 reconcile）

---

## 使用场景

**适用于**：
- apply 完成后，了解哪些测试用例已被代码覆盖
- 生成结构化的人工测试清单，交给 QA 执行
- 发现遗漏的边界保护逻辑

**不做**：
- 实际运行测试（AI 无法启动 Unity 或服务端进程）
- 替代人工联调（集成测试必须人工执行）

### 步骤 3：对每条 TC 分类

将测试用例分为 3 类：

| 类型 | 特征 | 处理方式 |
|-----|------|---------|
| **类型 1：静态可验证** | 纯逻辑判断（防重复、边界保护、状态机） | AI 追踪代码逻辑，输出验证结果 |
| **类型 2：集成测试** | 涉及 UI 交互、SDK 回调、网络通信 | 输出到人工测试清单 |
| **类型 3：联调测试** | 需要前后端真实交互、数据库查询 | 输出到联调测试清单 |

**分类规则**：

```
关键词匹配：
- "点击"、"弹窗"、"支付" → 类型 2（集成测试）
- "服务端发货"、"Record 表写入"、"协议返回" → 类型 3（联调测试）
- "按钮置灰"、"检查条件"、"防重复" → 类型 1（静态可验证）

操作步骤层数：
- 单步操作 + 纯客户端逻辑 → 类型 1
- 多步操作 + 涉及 SDK/网络 → 类型 2/3
```

## 技术要点

### 分类规则自动化

通过关键词 + 操作步骤层数自动分类：

```python
def classify_test_case(tc):
    keywords_integration = ["点击", "弹窗", "支付", "SDK"]
    keywords_e2e = ["服务端", "Record 表", "协议返回", "联调"]
    keywords_static = ["置灰", "检查", "防重复", "边界"]
    
    text = tc.operation + tc.expected
    
    if any(kw in text for kw in keywords_e2e):
        return "type3_e2e"
    elif any(kw in text for kw in keywords_integration):
        return "type2_integration"
    elif any(kw in text for kw in keywords_static):
        return "type1_static"
    else:
        return "type2_integration"  # 默认人工测试
```

### 静态验证策略

**CodeGraph 的能力边界**：
- ✅ 能做：返回符号定义、源码片段（如 `OnClickClaim` 函数体）
- ❌ 不能做：自动理解业务语义（如"这段代码实现了防重复逻辑"）

**实际执行流程**：
1. 用 CodeGraph 查询相关符号源码（如 `OnClickClaim`）
2. AI 阅读返回的源码，判断是否存在对应逻辑（如 `if (HasClaimed) return;`）
3. 输出验证结果和证据（代码位置 + 代码片段）

**这不是自动化验证，而是 AI 辅助的代码审查**。

**客户端逻辑验证**：
- 追踪按钮点击事件 → 找到处理函数 → AI 阅读源码检查 if 分支

**服务端逻辑验证**：
- 追踪协议处理函数 → AI 阅读源码检查权威校验逻辑 → 检查 Record 表写入

**无法验证的**：
- UI 实际显示效果（需要运行 Unity）
- 网络通信结果（需要真实联调）
- 性能表现（需要 Profiler）

### 人工测试清单格式

**必须包含**：
- TC ID（可追溯）
- 前置条件（环境准备）
- 操作步骤（可复现）
- 预期结果（验收标准）
- 验证点（关键检查项）
- 联调要求（需要哪些环境）

**分组原则**：
- 按功能模块分组（购买流程、领取流程、UI 显示）
- 同类型的 TC 放在一起（减少环境切换）

## 常见问题

### Q1: 静态验证的准确率如何？

**A**: 对于纯逻辑判断（if/else 分支、状态机），准确率 > 90%。对于涉及运行时状态的（Record 表数据、网络返回），无法验证。

---

### Q2: 人工测试清单是否需要全部执行？

**A**: 建议优先执行：
1. 核心流程（购买、领取）
2. 高严重度边界保护（背包满、重复领取）
3. 联调测试（前后端交互）

UI 显示类 TC 可根据项目规范选择性执行。

---

### Q3: 如果 test-cases.md 格式不标准怎么办？

**A**: 尽力解析，无法解析的 TC 标注"格式错误，请人工确认"，全部归入人工测试清单。
